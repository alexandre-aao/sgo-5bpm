# SGO 5º BPM — Sistema de Gestão Operacional

Aplicativo full-stack para a Seção de Planejamento (P3) do 5º Batalhão de Polícia Militar. Nasceu como "Pauta de Eventos" (gestão de eventos e diárias) e cresceu para cobrir também o Cartão Programa de patrulhamento diário, cadastros de referência (bairros, pessoal) e relatórios operacionais. Todo o domínio é em português — nomes de variáveis, campos de dados e textos de interface usam a terminologia da corporação (Ofício, diária, viatura, guarnição, Fiscal de Operações etc.).

## Stack e arquitetura

- **Backend:** Node.js + Express (CommonJS). `server.js` é o composition root: configura segurança, autenticação global e monta os routers de `routes/`; regras puras ficam em `lib/dominio.js`/`lib/recorrencia.js` e a camada Supabase em `lib/dados.js`. Sem TypeScript no backend.
- **Frontend:** React + TypeScript + Vite em `client/`, com rotas por módulo, componentes compartilhados e lazy loading. O antigo frontend vanilla em `public/` foi removido; não reintroduzir `public/app.js`, handlers delegados por `data-action` ou controle de perfil por `hidden-role`.
- **Banco de dados:** Supabase (Postgres). `lib/dados.js` cria o cliente com `service_role` (bypassa RLS; a autorização continua no Express por `autenticar`/`exigirP3`/`exigirEdicaoCartao`) e concentra `readDB`/`writeDB`, leituras pontuais e constantes compartilhadas. Nas quatro tabelas de maior concorrência (`cartoes`, `escalas`, `eventos`, `operacoes`), toda rota nova de escrita deve usar `writeRow`/`deleteRow`, nunca o diff de tabela inteira de `writeDB`. GETs de tabela única usam `readTabela(tabela, filtros)`; agregadores leem somente as tabelas de que precisam, normalmente em `Promise.all`. Schema final em `supabase/schema.sql`; mudanças são migrations SQL aditivas e idempotentes em `migrations/`, aplicadas manualmente no SQL Editor. Tabela/coluna nova deve ser refletida em `lib/dados.js` (`TABELAS`/`CHAVE_PRIMARIA`, quando aplicável).
- **Frontend com bundler (Vite) desde a migração React** — a afirmação anterior de que "npm só serve o backend" e de que Lucide e Leaflet vinham por CDN **está obsoleta**: os dois são dependências npm de `client/package.json` (`lucide-react`, `leaflet` + `@types/leaflet`), importadas em módulo e resolvidas no build. **A única CDN que resta é o Google Fonts** (Inter, em `client/index.html`).
- **Deploy:** Vercel, função serverless única (`server.js` via `@vercel/node`, ver `vercel.json`). Projeto conectado ao repositório GitHub `alexandre-aao/sgo-5bpm` — todo `git push` na branch `main` dispara deploy automático em produção (`https://sgo-5bpm.vercel.app`). Variáveis de ambiente `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` configuradas no painel da Vercel (Project Settings → Environment Variables), **não** commitadas — localmente ficam em `.env.local` (git-ignorado) e são carregadas também via `.claude/launch.json` pro preview server.
- **Não é monorepo.** Só existe este projeto neste diretório.

## Rodando o projeto

Pós-migração (Fase 6): `node server.js` sozinho só serve `/api/*` — não serve mais frontend nenhum (o antigo `public/` foi removido; em produção o frontend é o build estático de `/client`, servido pela Vercel via `@vercel/static-build`, não por Express). Pra rodar o app completo localmente, precisa dos **dois** processos:

```bash
npm test                  # node --test test/*.test.js — não precisa de Supabase nem servidor no ar

npm install               # backend, na raiz
npm start                 # ou: node server.js — API em :3005

cd client && npm install
npm run dev                # frontend Vite em :5173, aponta pra :3005 via VITE_API_BASE_URL
```

Ver `.claude/launch.json` (`autoPort: true` deixa o harness de preview escolher outra porta livre se 3005/5173 já estiverem em uso). Precisa de `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` no ambiente do backend — já configuradas em `.claude/launch.json`.

**Sempre reiniciar `node server.js`** depois de editar `server.js` — não há hot reload (o frontend em `client/` tem HMR via Vite, esse não precisa reiniciar). Se o usuário reportar "erro no servidor" em algo que você acabou de mudar, o primeiro suspeito é sempre um servidor real (`npm start` do próprio usuário, fora do preview do Claude Code) rodando código antigo sem reiniciar.

Pra conferir o build de produção do frontend localmente: `cd client && npm run build && npm run preview` (serve `client/dist` isolado, sem API — só serve pra checar se o build compila e renderiza; pra testar fluxos completos use o par `node server.js` + `npm run dev` acima).

## Modelo de dados (Supabase / Postgres)

- **`eventos`** — Eventos_Pauta: eventos **civis, sem diária** (Show, Futebol, Ato Público, Religioso, Cultural, Evento Junino, Outros). **Não têm mais escala nominal nem diária** — isso migrou para `operacoes` (ver abaixo). Campos-chave: `data_inicio`/`data_termino`, `bairro` (select alimentado por `bairros_coordenadas` + opção "Outro" com texto livre), `num_os_manual` e `num_sei` (texto livre, preenchidos manualmente — **não existe mais geração automática de código de OS nem status de OS/Kanban, foram removidos deliberadamente**).
- **`operacoes`** — registro **único** de operação policial (planejamento → execução, sem duplicar registro como fazia a antiga `missoes_planejadas`). Campos: os mesmos de `eventos` mais `tipo_operacao` (Ostensiva, Saturação, Cerco, Blitz, Cumprimento de Mandado, Reforço, Outras — em `TIPOS_OPERACAO` no `server.js`), `situacao` (`Planejada` | `Executada` — só muda via "Marcar como Executada", sem efeito colateral em diária), `qtd_diarias_estimada` (reserva de cota enquanto ainda não há escala), `tipo_recorrencia` (`diaria`|`fim_de_semana`|`dia_unico`, opcional). Diária da operação = `diariaDaOperacao(op, escalas)`: soma real das escalas se houver, senão a estimativa. É onde a diária vive agora. A antiga `missoes_planejadas` foi migrada para cá e a tabela ficou **órfã no banco** (dados migrados, sem `DROP`, sem código lendo — não recriar dependência nela).
  - **Recorrência (2026-08, migration `004_recorrencia_operacoes.sql`):** `grupo_recorrencia_id` (TEXT, `generateId('grp')`; null = operação avulsa) liga as ocorrências de um mesmo lote, e `recorrencia_regra` (JSONB) guarda a regra que as originou, **idêntica em todas**. Formato: `{ tipo: diaria|semanal|intervalo|avulsa, data_inicio, data_fim, dias_semana[], intervalo_dias, datas[], datas_excluidas[], total_ocorrencias }`. **Cada ocorrência é uma linha própria** (nada de geração virtual na leitura) e é de **UM dia** (`data_inicio = data_termino`) — o "fim" da recorrência vive em `recorrencia_regra.data_fim`. **`tipo_recorrencia` é OUTRO campo**, anterior e apenas descritivo: valores parecidos (`diaria`/`fim_de_semana`/`dia_unico`), semântica diferente, os dois coexistem. Seu select saiu do formulário em 2026-08 (ocupava o lugar semântico da recorrência real), mas a coluna e os valores das 7 operações antigas seguem intactos e preservados na edição.
- **`alocacoes`** — Alocacao_Policiamento: efetivo/viaturas alocados (modalidade, qtd_policiais, qtd_viaturas). Vinculada a **UM `evento_id` OU UM `operacao_id`** (nunca aos dois, nunca a nenhum — constraint `alocacoes_um_vinculo`).
- **`escalas`** — Escala_Diarias: militares escalados por **operação** (`operacao_id`, não mais `evento_id`). Regra de negócio fixa: **`total_diarias = qtd_aparicoes * 2`**. Sem trava por `situacao` — pode escalar em operação Planejada ou Executada.
  - **`militar_id` é a MATRÍCULA (RE), não o `pessoal.id`.** É texto livre, sem FK, e pode ser vazio — escalar quem não está no cadastro é permitido (o autocomplete aceita nome digitado). Por isso a identidade do militar usa `chaveMilitar(matricula, nome)`: `re:<matrícula>` ou, sem ela, `nome:<nome minúsculo>` — sem esse fallback, dois militares sem matrícula colidiriam numa chave vazia e um sobrescreveria o outro. A função está **duplicada** em `server.js` e em `client/src/lib/escalaLote.ts`; mudar num lado exige mudar no outro.
  - **`data` (DATE, migration 004)** — denormalização deliberada: antes a escala era datada só pela `data_inicio` da operação, e é assim que o Relatório Diário ainda agrupa. Com recorrência cada ocorrência é de um dia, então a coluna guarda a data **daquela ocorrência**. **Nullable e sem backfill** — escalas anteriores à migration têm `null` e todo leitor cai no fallback `operacao.data_inicio` (ver `resumoCotaEteto` no `server.js` e `calcularImpacto` no cliente).
  - **NÃO existe unique constraint em `(operacao_id, militar_id)`.** A duplicata que a impedia foi resolvida em 2026-08-06 (ver Pendências) e o banco está limpo, mas a constraint **segue não criada por decisão do usuário**. Motivo técnico que permanece: o `ON CONFLICT` reescreveria o `id` (PK) das linhas existentes. A idempotência do lote é por **leitura-e-escrita**, não por constraint.
- **`usuarios`** — login, senha (hash scrypt), `role` (`P3` | `Adjunto` | `Oficial`), nome. Conta de sistema (login), diferente de `pessoal`.
- **`pessoal`** — Cadastro de Pessoal: `nome`, `nome_guerra` (nome de guerra, texto livre — populado nos 244 registros; usado na busca do autocomplete de escala), `matricula` (RE, texto livre opcional), `subunidade` (lista fechada em `SUBUNIDADES_PESSOAL` no `server.js`: `PCS`, `1ª Companhia`, `2ª Companhia`, `3ª Companhia` — só descritivo, não tem lógica de negócio associada ainda), `posto_graduacao` (lista fechada da hierarquia PMRN em `POSTOS_GRADUACAO` no `server.js`), `tipo` (`Praça` | `Oficial`, derivado automaticamente do posto), `categorias[]` (`Adjunto`, `Fiscal de Operações`, `Oficial de Operações`, `Oficial de Sobreaviso`, `Executor` — uma pessoa pode ter mais de uma, ou nenhuma). Alimenta os seletores de Fiscal/Adjunto/Sobreaviso do Cartão Programa. `categorias` é opcional (decisão deliberada — o batalhão tem efetivo geral cadastrado só como registro, sem papel operacional ainda; não exigir categoria de volta sem confirmar com o usuário). O filtro "Sem categoria" na tela é só client-side (`app.js`), a API não tem esse filtro nativamente. Na importação de 2026-07 (ver "Pendências"), `categorias` foi inferida a partir da "Função Atual" do relatório SGEPM só nos casos inequívocos (função literal "Adjunto" → categoria Adjunto; funções de execução de patrulha — Comandante de VTR, Patrulheiro, Motorista de VTR, Guarda — → categoria Executor); funções de comando/plantão (Comandante do BPM, Delta 07 etc.) e administrativas ficaram deliberadamente sem categoria por ambiguidade — não inferir esse grupo automaticamente numa limpeza futura sem confirmar com o usuário, pois afeta diretamente os seletores reais de Fiscal/Oficial de Operações/Sobreaviso do Cartão Programa.
- **`bairros_coordenadas`** — `nome_bairro`, `latitude`, `longitude`, `ativo`. Seed inicial: 7 bairros da Zona Sul de Natal (coordenadas aproximadas de centróide, não geocodificação precisa). É o **único** cadastro de bairro do projeto: alimenta o select de Bairro em Novo Evento, os marcadores do Mapa, o vínculo da viatura no Cartão Programa e o escopo dos Avisos Operacionais. **Coordenada é opcional** (migration 001): um bairro pode existir só para receber aviso/vincular viatura, sem ser plotado. Quem lê lat/lng para o mapa usa o type guard `temCoordenada`/`bairrosPlotaveis` (`client/src/lib/bairros.ts`) — não assumir que existem.
- **`avisos`** — Avisos Operacionais criados pela P3: `bairro_id` e/ou `companhia` (constraint `aviso_tem_escopo` exige ao menos um), `categoria` (texto livre), `prioridade` (`informativa`|`atencao`|`alta`|`critica`), `texto` (≤240 no banco), vigência (`data_inicio`/`data_fim`/`permanente`) e `ativo`. Vigência padrão de 30 dias, calculada no servidor. **Fica FORA de `TABELAS`** de propósito: `readDB()` traria a tabela em toda rota agregadora sem usar. Usar `readTabela`/`writeRow`. Por isso `/api/backup` soma `avisos` explicitamente — ao criar tabela nova nesse padrão, lembrar do backup.
- **`contador_cartoes`** + função `proximo_numero_cartao(ano)` — numeração sequencial do Cartão Programa por ano (`000123/2026`), com a corrida resolvida no banco (`INSERT ... ON CONFLICT DO UPDATE`). O número é atribuído na **criação** do cartão, nunca na geração do PDF, para não mudar entre versões do mesmo cartão. Falha ao numerar não impede criar o cartão (loga e grava sem número; o índice único é parcial, `where numero is not null`).
- **`cartoes`** — Cartão Programa: um por data (`data`), com `viaturas[]` (prefixo, setor, companhia, categoria, comandante, observação) e `itens[]` de roteiro (horário início/fim, local, atividade). Campos de nível DIA acrescentados em 2026-07 (migration 001): `ano`/`numero` (numeração oficial), `fiscal_pessoal_id`/`adjunto_pessoal_id` (id do cadastro, fonte de verdade para o PDF montar "graduação + nome de guerra"), `fiscal_exibicao`/`adjunto_exibicao` e `delta07_viatura`. **"Delta 07" é o rótulo operacional do Fiscal de Operações** — mesmo campo, não um papel novo; por isso os campos são `fiscal_*`. O que é de nível VIATURA vive no JSONB de cada viatura, não em coluna: `bairro_id`, `comandante_pessoal_id`, `comandante_exibicao`, `avisos_ids[]`, `versao`, `status_envio`, `gerado_em`, `hash_conteudo`. Motivo: um cartão é um DIA com N viaturas, e status/versão do PDF são por viatura — em coluna valeriam para o dia inteiro e quebrariam o `_v2` individual. Viaturas gravadas antes da migration não têm esses campos e **não há migração de boot preenchendo** (reescreveria todos os cartões à toa): todo leitor trata a ausência com `|| ''`. Campos de cabeçalho `fiscal`, `adjunto`, `oficial_sobreaviso` guardam o **nome** da pessoa selecionada (não um id — mantém compatibilidade com cartões antigos que tinham texto livre). Também serve de **padrão**: `is_template` (bool), `nome_template`, `tipo_periodo` (`semana` | `fim_de_semana`), `qtd_viaturas_base` (5/6/7), `origem_template_id` (rastreia de qual padrão um cartão do dia foi clonado). Padrões têm `data: null` e nunca aparecem nas listagens normais por data.
  - **Padrão único (2026-07, migration `002_cartao_padrao_unico.sql`):** coluna `padrao_ativo` (boolean) restrita a `is_template=true` (CHECK `cartoes_padrao_so_template`), com índice único parcial `ux_cartoes_padrao_unico` garantindo **um só** `padrao_ativo=true` no sistema inteiro. A troca é feita **só** pela função `ativar_cartao_padrao(p_id)` (plpgsql, `security definer`, revogada de `anon`/`authenticated`) — nunca por dois `UPDATE` separados: índice único não é deferível, e duas chamadas HTTP sequenciais deixariam uma janela sem padrão nenhum. Templates nomeados múltiplos continuam existindo (histórico de padrões, ver `GET /api/cartoes/templates`), mas só o `padrao_ativo` é usado para clonar o cartão do dia — o antigo fluxo "Copiar de qualquer cartão" (`copiar_de`) e a rota `POST /api/cartoes/:id/clonar` foram **removidos**.
- **`sessoes`** — tokens de autenticação ativos (expiram em 12h).
- **`config`** — `cota_mensal_diarias`.

### Regras de negócio importantes

- **Diária:** `qtd_aparicoes * 2`, sempre. Não mexer nessa fórmula sem confirmar com o usuário. **Diária é das `operacoes`, não dos `eventos`** (eventos civis não geram diária). No Planejador: `total_consumido` = soma real das escalas das operações que já têm escala; `total_planejado` = soma de `qtd_diarias_estimada` só das operações **sem** escala. Nunca a mesma operação nos dois — evita contagem dupla. Ver `diariaDaOperacao` no `server.js`.
- **Recorrência e ações de grupo (2026-08):** o motor (`lib/recorrencia.js`) é **puro e opera em UTC** — `gerarDatasRecorrencia(regra)` não usa `Date.now()` nem hora local, porque a Vercel roda em UTC e a máquina do batalhão em `America/Fortaleza`, e `new Date('2026-08-03').getDay()` daria um dia a menos em todo fuso a oeste de Greenwich. Dias da semana no padrão `Date.getDay()`: **domingo = 0 … sábado = 6** (seg/qua/sex = `[1,3,5]`). Limites de **92 ocorrências por lote** e **janela de 12 meses**, validados no servidor (a UI não é autoridade) e medidos sobre a geração **bruta**, antes das exclusões. As ações de grupo (`PUT`/`DELETE /api/operacoes/grupo/:grupoId?escopo=`) aceitam `somente_esta` | `esta_e_futuras` | `todas`; as duas primeiras exigem `?ref=<id da ocorrência>`. `PUT` de grupo **não altera datas nem `situacao`** (HTTP 400): mudar a data do grupo inteiro é *regerar* o grupo, não editá-lo.
- **Ocorrência `Executada` nunca é tocada por ação de grupo ou de lote** — nem editada, nem excluída, nem escalada. É registro histórico do que a tropa cumpriu. Vale em `PUT`/`DELETE /api/operacoes/grupo/:grupoId`, `POST`/`DELETE /api/escalas/lote` e na contagem de impacto da UI (`operacoesDoEscopo` em `client/src/lib/escalaLote.ts` já as remove — incluí-las faria a tela prometer mais do que grava). **Exceção:** `POST /api/escalas` unitário segue sem essa trava, e é o único caminho que aceita escalar em operação Executada — mas **nenhuma tela o usa desde 2026-08**, então não há caminho de UI para isso.
- **Teto de 20 diárias por militar no mês (`TETO_DIARIAS_MILITAR_MES`) é ALERTA, nunca bloqueio** — igual à cota mensal. Nenhuma rota recusa por causa dele e o botão de confirmar segue habilitado; quem decide escalar além disso é a P3. Vale nos dois lados (`resumoCotaEteto` no `server.js`, `calcularImpacto` no cliente). **Auxílio-Alimentação não existe em lugar nenhum do sistema** — se aparecer num pedido como "vínculo 1:1 a preservar", não há o que preservar.
- **Não existe mais status de evento nem Kanban de Ordem de Serviço** — foi removido deliberadamente (era `status_os`/`codigo_os`/Kanban no Dashboard). Não reintroduzir sem pedido explícito do usuário. No lugar: `num_os_manual` e `num_sei`, campos de texto livre preenchidos manualmente. O Dashboard alerta quando um evento próximo/em andamento está sem Número da OS e/ou Número SEI informado (calculado, não é status manual).
- **Praça x Oficial no Cartão Programa:** se o Fiscal de Operações selecionado for classificado como `Praça` (posto/graduação até Subtenente) e o campo Oficial de Sobreaviso estiver vazio, o sistema mostra um alerta **não-bloqueante** no painel de Alertas de Conflito do Cartão — não impede salvar.
- **Padrão único de Cartão Programa (2026-07):** um único padrão global ativo por vez (ver `cartoes.padrao_ativo` em "Modelo de dados"). `POST /api/cartoes` (sem `is_template`) **sempre** clona o padrão ativo — 409 tratado (nunca 500) se não houver nenhum. P3 troca o padrão ativo em `PUT /api/cartoes/:id/padrao-ativo` (`exigirP3`), um clique na tela ("Definir como padrão" no painel de Templates). O clone zera `comandante` e o controle de envio (`camposEnvioIniciais()`), herda `bairro_id`/`tipo_periodo`/`qtd_viaturas_base` e grava `origem_template_id`. **Não há mais** busca por tipo de período/quantidade de viaturas nem cópia de "qualquer cartão existente" — a UI (`CriarDoPadrao.tsx`, antigo `SugestaoTemplate.tsx`) só mostra o padrão ativo e um botão "Criar Cartão do Padrão". `tipo_periodo` continua editável no cabeçalho via `PUT /api/cartoes/:id` (Adjunto pode).
- **Perfis de acesso:**
  - `P3` — acesso total (admin), incluindo Cadastro de Pessoal, Cadastro de Bairros e gestão de Templates/Padrão do Cartão Programa.
  - `Adjunto` / `Oficial` — só veem Meu Turno, Cartão Programa, Listar Eventos e Mapa (leitura). Cartão Programa é a única coisa que eles podem *editar* — inclusive criar o cartão do dia a partir do padrão ativo, que não exige P3 de propósito. A aba **Operações** é P3-only. **Exceção deliberada: Cadastro de Viaturas** também fica aberto a Adjunto/Oficial — podem cadastrar e editar viaturas (não só ler); só a exclusão é P3-only (`DELETE /api/viaturas/:id` com `exigirP3`; `POST`/`PUT` de propósito sem o middleware).
  - **Middleware `exigirEdicaoCartao` (2026-07):** as 8 rotas de escrita de viatura/item/cabeçalho do cartão (`PUT /api/cartoes/:id`, `POST`/`PUT`/`DELETE` de `/viaturas` e `/viaturas/:vid/itens`) bloqueiam `Oficial` (403) — antes não checavam perfil nenhum. Cada handler também bloqueia `Adjunto` inline quando `cartao.is_template=true` (só P3 edita um padrão). **Nunca usar `exigirP3` aqui** — bloquearia o Adjunto, que por decisão de produto edita o Cartão Programa do dia livremente.
  - **Janela de exclusão do Cartão Programa (2026-07):** o Adjunto pode excluir o cartão de **um dia** até as **07h00 do dia seguinte** à data do serviço; depois disso o roteiro já foi cumprido e vira registro histórico, e só o P3 exclui. Template segue P3-only em qualquer horário (é estrutura reaproveitada, não roteiro de um dia). Oficial não exclui. `America/Fortaleza` é **UTC-3 fixo** (sem horário de verão desde 2019), então o offset é literal — sem lib de fuso, o que importa porque a Vercel roda em UTC. Regra duplicada nos dois lados: `dentroDaJanelaExclusaoAdjunto` em `server.js` (decide) e `client/src/lib/janelaCartao.ts` (só esconde o botão).
- **Janela de 24h do Cartão Programa (2026-07):** a janela do cartão vai das **07h00 da `data`** até **07h00 do dia seguinte** — não é um dia de calendário. A ordenação do roteiro (`ordenarPorTurno` em `server.js`, aplicada na leitura e ao inserir/editar item) usa a âncora circular `((minutos - 420) + 1440) % 1440`: um item às 06h30 ordena depois de um às 23h00. `client/src/lib/janelaCartao.ts` espelha isso na exibição — `janela24h(data)` formata o período completo ("05/08/2026 07h00 às 06/08/2026 07h00", nunca a data isolada) e `marcarViradaDeDia(itens, data)` intercala um marcador textual (`— 06/08 —`) entre o último item de hoje (≥07h00) e o primeiro de amanhã (&lt;07h00), sem agrupar nem reordenar. Consumido em `CartaoHeader.tsx`, `ViaturaRoteiroCard.tsx`, `pdf/cartaoPdfDados.ts` (campo `janela`) e na Central de Impressão.
- Controle de acesso é **client-side E server-side** — sempre implementar os dois lados, nunca confiar só no frontend. No React o lado do cliente é `RequireRole.tsx` (guarda de rota) + `navConfig.ts` (quais destinos o perfil vê); a classe `hidden-role` do app vanilla **não existe mais**. No servidor, `exigirP3` / `exigirEdicaoCartao`.

## Segurança (já implementada — não regredir)

- Senhas com hash `scrypt` (nunca texto puro). Migração automática de senhas legadas roda no boot do servidor.
- **Sessão em cookie `HttpOnly` (Fase 4, 2026-08).** O token saiu do `localStorage` — onde qualquer XSS o leria — para um cookie `sgo_sessao` `HttpOnly` + `SameSite=Strict` (+ `Secure` só em produção: em `http://localhost` o navegador recusaria e o login local pararia). **A transição é compatível nos dois lados:** `autenticar` aceita cookie **OU** o Bearer antigo (`tokenDaRequisicao`), e o cliente segue mandando Bearer enquanto houver token legado salvo — ninguém é deslogado no deploy. O login novo não persiste mais o token; `localStorage['user']` guarda só a identidade para a UI. `apiFetch` usa `credentials: 'include'` (sem isso o cookie não viaja no dev, onde 5173 → 3005 é cross-origin) e o CORS tem `credentials: true`. **CSRF:** `SameSite=Strict` já impede o envio cross-site; a segunda camada é a checagem de `Origin` em `autenticar`, aplicada **só** a quem se autenticou por cookie — o Bearer exige que o JS leia o token, o que outro site não consegue. Ao remover a compatibilidade Bearer, tirar também `setAuthToken` e o `token` da resposta do login.
- **O callback do CORS nega sem lançar.** Lançar `Error` ali virava HTTP 500 **com stack trace no corpo**, expondo caminhos do servidor justamente a quem veio de origem hostil. `callback(null, false)` faz a resposta sair sem os cabeçalhos CORS e o navegador bloquear.
- Sessões via token Bearer, expiram em 12h, invalidadas no logout. Sessões expiradas de qualquer usuário são apagadas globalmente no boot do servidor (dentro do IIFE `inicializar()`), além da limpeza pontual das sessões expiradas do próprio usuário que já acontecia a cada login.
- Toda rota `/api/*` (exceto `/api/login`) exige token válido (middleware `autenticar`), que popula `req.user = { usuario, role, nome }`.
- Rotas de escrita administrativas exigem `exigirP3`. `POST /api/cartoes` faz a checagem de role manualmente dentro do handler (em vez de usar o middleware) só quando `is_template` é true, porque a mesma rota também cria o cartão do dia — que Adjunto/Oficial podem criar livremente — ler o handler antes de assumir que uma rota tem ou não restrição. `DELETE /api/cartoes/:id` usa o middleware `exigirP3` para qualquer cartão (template ou do dia) — apagar o roteiro operacional de um dia é destrutivo e não faz parte da edição diária que Adjunto/Oficial têm permissão de fazer no Cartão Programa.
- **Escape de HTML contra XSS:** no React o escape é automático — **não** envolver valor em `esc()` dentro de JSX (produziria `&amp;` visível). A função `esc()` (`client/src/lib/esc.ts`) continua existindo e é **obrigatória** no único lugar onde o app monta markup cru: os `bindPopup()` do Leaflet em `MapaLeaflet.tsx`. Hoje não há nenhum `innerHTML` nem `dangerouslySetInnerHTML` no projeto; ao introduzir um, `esc(...)` volta a ser obrigatório.
- Senha mínima: **3 caracteres** (decisão deliberada, para não quebrar a senha padrão `123` já usada pelo batalhão — não "corrigir" para 4+ sem perguntar).
- **RLS habilitado em todas as tabelas públicas** (migration `ativar_rls_tabelas_publicas`, 2026-07), **sem policies**. O `service_role` que o `server.js` usa tem `BYPASSRLS`, então RLS não afeta nenhuma rota do backend; sem policy, os roles `anon`/`authenticated` ficam totalmente bloqueados no acesso direto ao Supabase (o frontend não fala com o Supabase direto). Isso fecha o alerta `rls_disabled_in_public` do Supabase. Ao criar tabela nova, habilitar RLS nela também (`ALTER TABLE ... ENABLE ROW LEVEL SECURITY`, sem policy) — ver bloco no fim de `supabase/schema.sql`. **Não** criar policies sem necessidade real (quebraria o padrão de autorização feito no Express).

- **Ordem de registro das rotas no Express (armadilha real, 2026-08):** `app.post('/api/escalas/lote')` e `app.delete('/api/escalas/lote')` **precisam ser registradas ANTES** de `PUT`/`DELETE /api/escalas/:id`. `/lote` tem um segmento só, igual a `:id` — na ordem inversa o Express casa `"lote"` como se fosse um id e a rota de lote nunca é alcançada. As rotas de **grupo** (`/api/operacoes/grupo/:grupoId`) não têm esse problema porque têm dois segmentos depois do prefixo. **Ao criar qualquer rota com caminho literal sob um prefixo que já tem `:id`, registrar o literal primeiro.**
- **Migrações de schema:** IIFE no topo do `server.js` (junto das outras, ex. `normalizarCamposTemplateCartao`, `seedBairrosCoordenadas`) que roda no boot, lê o db, adiciona campos faltantes com `if (!('campo' in obj))`, e só grava (`writeDB`) se algo mudou. Nunca destrutivo.

## Shell, atalhos e estados de carga (Fase 2/2B, 2026-08)

- **Paleta de comandos (Ctrl+K)** — `components/paleta/`. Busca eventos, operações, pessoal e bairros (via `normalizarTexto`), navega e dispara ações rápidas. Os resultados são **filtrados pelo perfil** — não como segurança (as rotas do servidor continuam sendo a autoridade), mas para não oferecer atalho que termina em 403. Limite de **5 por grupo**; sem termo digitado mostra só navegação e ações.
- **`useParametroInicial`** (`hooks/`) consome **uma vez** um parâmetro da URL e o remove (`replace`). É o que faz os destinos da paleta e do Dashboard abrirem o registro certo: `/eventos?evento=<id>` abre a gaveta, `/operacoes?operacao=<id>` idem, `/pessoal?busca=`, `/eventos?de=&ate=`. **Nenhuma dessas telas lia query param antes** — sem o hook, o link levava à tela e ignorava o registro. Use a **forma funcional** de `setSearchParams` ao mexer nele: com dois parâmetros na mesma tela os efeitos rodam no mesmo render, e uma cópia do objeto devolveria à URL o parâmetro que o outro acabou de remover.
- **Atalhos** (`hooks/useAtalhosGlobais.ts`): `Ctrl/Cmd+K` paleta, `N` novo da tela ativa, `?` ajuda, `←/→` dia no Cartão. **Regra**: tecla simples nunca é capturada com o foco num campo de digitação — só combinação com modificador. `N` viaja por **CustomEvent** (`useAtalhoNovo`) porque o botão de criar vive dentro de cada página com estado próprio; levantar esse estado até o layout acoplaria todas as telas ao shell. **`useAtalhoSetasDia` é hook separado de propósito** — quando o Cartão usava o hook global só para receber as setas, existiam dois listeners tratando `N` e o evento disparava duas vezes.
- **Esqueletos** (`components/estado/Esqueleto.tsx`): use **spinner** (`Carregando`) quando não se sabe o formato do que vem e **esqueleto** quando já se sabe (KPIs, linhas de tabela). Ligados nos KPIs do Dashboard e na tabela de Pessoal. A animação respeita `prefers-reduced-motion`.
- **`carregandoSecundario`** no `AppDataContext` existe por causa da 2ª onda: `pessoal`/`viaturas` chegam **depois** da tela pintada, então sem o sinal a tabela de Pessoal aparecia vazia — indistinguível de "nada cadastrado". A flag também é desligada no `catch`, senão uma falha da 2ª onda prenderia a tabela num esqueleto eterno.
- **`atualizadoEm` / `IndicadorFrescor`** — "Atualizado às HH:MM" + refresh manual na topbar. O polling de 60s é invisível, e quando a rede falha o app **preserva os dados anteriores de propósito** (`usarLista`), o que torna o horário a única pista de que estão velhos.
- **Formulário longo como painel lateral**: `ModalOperacao` e `ModalAviso` recebem `overlay-painel` + `modal-box-painel` e viram painel de 560px à direita **a partir de 1024px**; abaixo disso vale o bottom sheet do celular. `useModalA11y` continua igual — mudam só duas classes.
- **Mobile (Fase 2)**: `viewport-fit=cover` no `client/index.html` é o que faz os `env(safe-area-inset-*)` já espalhados pelo CSS valerem alguma coisa no iOS. Campos vão a **16px no celular** — é o limiar exato que desarma o zoom automático do Safari, não escolha tipográfica. `.btn`/`.btn-icon` têm 44px de alvo. O bloco de correções mobile fica **no fim do `style.css`** de propósito: são regras transversais que precisam vencer as de componente.
- **PWA instalável** (sem service worker, sem cache offline): `client/public/manifest.webmanifest` + ícones em `client/public/icons/`, gerados do brasão original de 1920×2192 (o de `public/img` tem 112×128 e só daria upscale). Os `maskable` levam o brasão a 60% do lado, dentro da área segura do círculo.

## Testes, lint e CI (2026-08)

- **`npm test`** (raiz) — `node --test test/*.test.js`, sem Supabase nem servidor no ar. Cobre `lib/recorrencia.js` (motor de recorrência), `lib/dominio.js` (regras puras extraídas do `server.js`) e `test/paridade.test.js`.

Fluxo P3-only em Administração (painel colapsável na aba Usuários) para recortar histórico consolidado — o banco só cresce.

Como as contagens entram no HMAC, qualquer cadastro feito entre o export e a confirmação invalida o comprovante e o servidor manda exportar de novo — nunca se apaga o que ninguém baixou.
- **Data de corte anterior a 6 meses**, validado no servidor: arquivamento é para histórico consolidado, e a trava protege de uma data recente digitada por engano.
- Exclusão em **lotes de 100 ids** (um `.in()` com centenas estoura o limite de URL do PostgREST) e na ordem **dependentes primeiro** (`escalas`, `alocacoes`, depois `eventos`, `operacoes`), senão sobram órfãs.

**⚠️ O Lote 6 NÃO é find-and-replace — medido em 2026-08.** Trocar `style={{ width: 14, height: 14 }}` por uma classe utilitária parece mecânico e **não é**: `style` inline vence tudo, mas uma classe simples (0,1,0) **perde** para as ~30 regras que já dimensionam `svg`, várias mais específicas (`.btn-icon svg` = 0,1,1; `.btn-icon.btn-sm svg` = 0,2,1). Os 15 casos de tamanho de ícone inline se dividem em três categorias, e só a primeira é segura:
- **Redundante** — o inline repete o valor que a regra já aplica (14px dentro de `.btn-icon.btn-sm`). Remover é no-op comprovado pela cascata. **Os 6 casos assim já foram removidos.**
- **Override intencional** — o inline difere da regra de propósito (`AlocacoesList` usa 12px onde `.btn-icon.btn-sm svg` daria 14px). Trocar por classe **muda o tamanho na tela**; exige decisão visual, não migração.
- **Sem regra concorrente** — ícone dentro de `.btn` comum (`TemplatesPanel`, `GradeEdicao`). Aqui a classe funcionaria, mas confira o container antes.

Regra prática: **antes de trocar um `style` de ícone por classe, verifique a cascata do container**. O ganho é de manutenção e o risco é regressão que ninguém vê.
