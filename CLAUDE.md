# SGO 5º BPM — Sistema de Gestão Operacional

Aplicativo full-stack para a Seção de Planejamento (P3) do 5º Batalhão de Polícia Militar. Nasceu como "Pauta de Eventos" (gestão de eventos e diárias) e cresceu para cobrir também o Cartão Programa de patrulhamento diário, cadastros de referência (bairros, pessoal) e relatórios operacionais. Todo o domínio é em português — nomes de variáveis, campos de dados e textos de interface usam a terminologia da corporação (Ofício, diária, viatura, guarnição, Fiscal de Operações etc.).

## Stack e arquitetura

- **Backend:** Node.js + Express, arquivo único `server.js`. Sem TypeScript, sem framework de rotas além do Express puro.
- **Frontend:** HTML/CSS/JS vanilla, sem build step, sem framework (nada de React/Vue). SPA por abas: todo o HTML das telas fica em `public/index.html` dentro de `<section class="tab-content">`, escondido/mostrado via classe `active`.
- **Banco de dados:** Supabase (Postgres). `server.js` acessa via `@supabase/supabase-js` com a chave `service_role` (bypassa RLS; a autorização é toda feita pelo próprio app — `autenticar`/`exigirP3`). Para preservar a lógica de negócio já escrita em JS puro (filter/map/reduce) sem reescrever tudo em SQL, existe um shim `readDB()`/`writeDB()` em `server.js` que busca/grava cada tabela inteira e monta o mesmo formato de objeto que o código já esperava do antigo `data/db.json`. `writeDB(db, tabelas)` recebe a lista explícita de tabelas alteradas por aquela escrita — nunca sincroniza as 8 tabelas inteiras à toa. Mesmo assim, `writeDB` faz upsert+diff da tabela inteira (não só da linha alterada), o que pode causar "lost update" entre duas escritas concorrentes na mesma tabela; nas quatro tabelas de maior concorrência (`cartoes`, `escalas`, `eventos`, `operacoes`) as rotas de escrita usam os helpers pontuais `writeRow(tabela, row)`/`deleteRow(tabela, id)` em vez de `writeDB`, evitando o read-modify-write da tabela inteira — ao adicionar uma nova rota de escrita nessas quatro tabelas, usar `writeRow`/`deleteRow`, não `writeDB`. As demais tabelas continuam no padrão `writeDB` original. Rotas quentes (`autenticar`, `/api/login`) usam consultas pontuais (`buscarSessaoPorToken`, `buscarUsuarioPorLogin`) em vez do shim. Os `POST`/`PUT` de `eventos` e `operacoes` leem a linha atual com `buscarRow(tabela, id)` (1 SELECT por id via `.eq().maybeSingle()`) em vez de `readDB()` — o `POST` nem lê (grava direto via `writeRow`). **Rotas GET de tabela única** (`/api/eventos`, `/api/operacoes`, `/api/pessoal`, `/api/escalas`, `/api/alocacoes`, `/api/viaturas`, `/api/bairros-coordenadas`) usam o helper `readTabela(tabela, filtros = {})` (`SELECT *` de UMA tabela, `.eq()` por filtro; valor vazio/undefined é ignorado) em vez de `readDB()` — evita baixar as outras 9 tabelas à toa (`readDB` fazia ~11 SELECTs por request; o boot do frontend eram ~77). Filtros por igualdade vão no objeto (`readTabela('escalas', { operacao_id })`); filtros por array (categoria de `pessoal`) e ordenação (`localeCompare`) continuam em JS. `config` é linha única → `buscarConfig()`. No cliente, o `fetchData` (`app.js`) carrega em **duas ondas**: 1ª o núcleo (`eventos`/`operacoes`/`alocacoes`/`escalas`/`config`), que já dispara `updateStats()` e a pintura da aba ativa (Dashboard/Turno); 2ª `pessoal` (244 linhas, o payload mais pesado) + `viaturas` logo depois, sem travar a 1ª pintura — tira o payload pesado do lote crítico no celular. Nenhuma aba de entrada padrão depende de pessoal/viaturas; as abas que os usam (Cartão/Operações/Mapa/autocomplete de escala) leem `state` ao vivo no render e degradam com fallback, então a 2ª onda não exige re-render. `fetchData` segue sendo chamado inteiro (as duas ondas) pelo polling de 60s, `visibilitychange` e refresh pós-escrita. **Ao criar uma GET nova de tabela única, usar `readTabela`, não `readDB`.** As rotas **agregadoras** (que cruzam várias tabelas: `dashboard-resumo`, `estatisticas*`, `relatorio*`, `planejador-diarias`, `diarias-calendario`) continuam com `readDB()`. Respostas são comprimidas com `compression()` (gzip) e os estáticos têm `Cache-Control: max-age=3600` (assets) / `no-cache` (index.html). **Cache-busting:** as referências a `app.js`/`style.css` no `index.html` recebem `?v=<ASSET_VERSION>` — como o `index.html` é `no-cache`, o HTML novo (com a nova versão) chega na hora e o navegador refetcha os assets em vez de servir os de até 1h atrás do cache. `ASSET_VERSION` = `VERCEL_GIT_COMMIT_SHA` (8 chars, muda a cada deploy na Vercel automaticamente) com fallback pro `mtime` do `app.js` em dev local. O `index.html` **não é mais servido pelo `express.static`** (que agora tem `index: false`): existe uma rota `app.get(['/', '/index.html'])` que serve uma cópia do HTML pré-lida no boot com o `?v=` já injetado (`INDEX_HTML`) — ao adicionar novo `<script>`/`<link>` versionável no `index.html`, incluir a substituição correspondente nesse bloco do `server.js`. Schema completo em `supabase/schema.sql` — mudanças de schema são SQL aditivo (`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`) rodado manualmente pelo usuário no SQL Editor do Supabase (não há migration runner automático), e a tabela nova/coluna nova entra em `TABELAS`/`CHAVE_PRIMARIA` no topo do `server.js`.
- **Sem dependências de frontend via bundler** (npm só serve o backend). CDNs usados: Lucide (ícones, versão fixada em `index.html` — ex: `lucide@1.24.0` — nunca usar `@latest`, evita quebra de ícones por update não controlado da lib), Google Fonts, **Leaflet** (mapa, aba Mapa).
- **Deploy:** Vercel, função serverless única (`server.js` via `@vercel/node`, ver `vercel.json`). Projeto conectado ao repositório GitHub `alexandre-aao/sgo-5bpm` — todo `git push` na branch `main` dispara deploy automático em produção (`https://sgo-5bpm.vercel.app`). Variáveis de ambiente `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` configuradas no painel da Vercel (Project Settings → Environment Variables), **não** commitadas — localmente ficam em `.env.local` (git-ignorado) e são carregadas também via `.claude/launch.json` pro preview server.
- **Não é monorepo.** Só existe este projeto neste diretório.

## Rodando o projeto

Pós-migração (Fase 6): `node server.js` sozinho só serve `/api/*` — não serve mais frontend nenhum (o antigo `public/` foi removido; em produção o frontend é o build estático de `/client`, servido pela Vercel via `@vercel/static-build`, não por Express). Pra rodar o app completo localmente, precisa dos **dois** processos:

```bash
npm install               # backend, na raiz
npm start                 # ou: node server.js — API em :3005

cd client && npm install
npm run dev                # frontend Vite em :5173, aponta pra :3005 via VITE_API_BASE_URL
```

Ver `.claude/launch.json` (`autoPort: true` deixa o harness de preview escolher outra porta livre se 3005/5173 já estiverem em uso). Precisa de `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` no ambiente do backend — já configuradas em `.claude/launch.json`.

**Sempre reiniciar `node server.js`** depois de editar `server.js` — não há hot reload (o frontend em `client/` tem HMR via Vite, esse não precisa reiniciar). Se o usuário reportar "erro no servidor" em algo que você acabou de mudar, o primeiro suspeito é sempre um servidor real (`npm start` do próprio usuário, fora do preview do Claude Code) rodando código antigo sem reiniciar.

Pra conferir o build de produção do frontend localmente: `cd client && npm run build && npm run preview` (serve `client/dist` isolado, sem API — só serve pra checar se o build compila e renderiza; pra testar fluxos completos use o par `node server.js` + `npm run dev` acima).

## Modelo de dados (Supabase / Postgres)

- **`eventos`** — Eventos_Pauta: eventos **civis, sem diária** (Show, Futebol, Ato Público, Religioso, Cultural, Evento Junino, Outros). **Não têm mais escala nominal nem diária** — isso migrou para `operacoes` (ver abaixo). Campos-chave: `data_inicio`/`data_termino`, `bairro` (select alimentado por `bairros_coordenadas` + opção "Outro" com texto livre), `num_os_manual` e `num_sei` (texto livre, preenchidos manualmente — **não existe mais geração automática de código de OS nem status de OS/Kanban, foram removidos deliberadamente**).
- **`operacoes`** — registro **único** de operação policial (planejamento → execução, sem duplicar registro como fazia a antiga `missoes_planejadas`). Campos: os mesmos de `eventos` mais `tipo_operacao` (Ostensiva, Saturação, Cerco, Blitz, Cumprimento de Mandado, Reforço, Outras — em `TIPOS_OPERACAO` no `server.js`), `situacao` (`Planejada` | `Executada` — só muda via "Marcar como Executada", sem efeito colateral em diária), `qtd_diarias_estimada` (reserva de cota enquanto ainda não há escala), `tipo_recorrencia` (`diaria`|`fim_de_semana`|`dia_unico`, opcional). Diária da operação = `diariaDaOperacao(op, escalas)`: soma real das escalas se houver, senão a estimativa. É onde a diária vive agora. A antiga `missoes_planejadas` foi migrada para cá e a tabela ficou **órfã no banco** (dados migrados, sem `DROP`, sem código lendo — não recriar dependência nela).
- **`alocacoes`** — Alocacao_Policiamento: efetivo/viaturas alocados (modalidade, qtd_policiais, qtd_viaturas). Vinculada a **UM `evento_id` OU UM `operacao_id`** (nunca aos dois, nunca a nenhum — constraint `alocacoes_um_vinculo`).
- **`escalas`** — Escala_Diarias: militares escalados por **operação** (`operacao_id`, não mais `evento_id`). Regra de negócio fixa: **`total_diarias = qtd_aparicoes * 2`**. Sem trava por `situacao` — pode escalar em operação Planejada ou Executada.
- **`usuarios`** — login, senha (hash scrypt), `role` (`P3` | `Adjunto` | `Oficial`), nome. Conta de sistema (login), diferente de `pessoal`.
- **`pessoal`** — Cadastro de Pessoal: `nome`, `nome_guerra` (nome de guerra, texto livre — populado nos 244 registros; usado na busca do autocomplete de escala), `matricula` (RE, texto livre opcional), `subunidade` (lista fechada em `SUBUNIDADES_PESSOAL` no `server.js`: `PCS`, `1ª Companhia`, `2ª Companhia`, `3ª Companhia` — só descritivo, não tem lógica de negócio associada ainda), `posto_graduacao` (lista fechada da hierarquia PMRN em `POSTOS_GRADUACAO` no `server.js`), `tipo` (`Praça` | `Oficial`, derivado automaticamente do posto), `categorias[]` (`Adjunto`, `Fiscal de Operações`, `Oficial de Operações`, `Oficial de Sobreaviso`, `Executor` — uma pessoa pode ter mais de uma, ou nenhuma). Alimenta os seletores de Fiscal/Adjunto/Sobreaviso do Cartão Programa. `categorias` é opcional (decisão deliberada — o batalhão tem efetivo geral cadastrado só como registro, sem papel operacional ainda; não exigir categoria de volta sem confirmar com o usuário). O filtro "Sem categoria" na tela é só client-side (`app.js`), a API não tem esse filtro nativamente. Na importação de 2026-07 (ver "Pendências"), `categorias` foi inferida a partir da "Função Atual" do relatório SGEPM só nos casos inequívocos (função literal "Adjunto" → categoria Adjunto; funções de execução de patrulha — Comandante de VTR, Patrulheiro, Motorista de VTR, Guarda — → categoria Executor); funções de comando/plantão (Comandante do BPM, Delta 07 etc.) e administrativas ficaram deliberadamente sem categoria por ambiguidade — não inferir esse grupo automaticamente numa limpeza futura sem confirmar com o usuário, pois afeta diretamente os seletores reais de Fiscal/Oficial de Operações/Sobreaviso do Cartão Programa.
- **`bairros_coordenadas`** — `nome_bairro`, `latitude`, `longitude`, `ativo`. Seed inicial: 7 bairros da Zona Sul de Natal (coordenadas aproximadas de centróide, não geocodificação precisa). É o **único** cadastro de bairro do projeto: alimenta o select de Bairro em Novo Evento, os marcadores do Mapa, o vínculo da viatura no Cartão Programa e o escopo dos Avisos Operacionais. **Coordenada é opcional** (migration 001): um bairro pode existir só para receber aviso/vincular viatura, sem ser plotado. Quem lê lat/lng para o mapa usa o type guard `temCoordenada`/`bairrosPlotaveis` (`client/src/lib/bairros.ts`) — não assumir que existem.
- **`avisos`** — Avisos Operacionais criados pela P3: `bairro_id` e/ou `companhia` (constraint `aviso_tem_escopo` exige ao menos um), `categoria` (texto livre), `prioridade` (`informativa`|`atencao`|`alta`|`critica`), `texto` (≤240 no banco), vigência (`data_inicio`/`data_fim`/`permanente`) e `ativo`. Vigência padrão de 30 dias, calculada no servidor. **Fica FORA de `TABELAS`** de propósito: `readDB()` traria a tabela em toda rota agregadora sem usar. Usar `readTabela`/`writeRow`. Por isso `/api/backup` soma `avisos` explicitamente — ao criar tabela nova nesse padrão, lembrar do backup.
- **`contador_cartoes`** + função `proximo_numero_cartao(ano)` — numeração sequencial do Cartão Programa por ano (`000123/2026`), com a corrida resolvida no banco (`INSERT ... ON CONFLICT DO UPDATE`). O número é atribuído na **criação** do cartão, nunca na geração do PDF, para não mudar entre versões do mesmo cartão. Falha ao numerar não impede criar o cartão (loga e grava sem número; o índice único é parcial, `where numero is not null`).
- **`cartoes`** — Cartão Programa: um por data (`data`), com `viaturas[]` (prefixo, setor, companhia, categoria, comandante, observação) e `itens[]` de roteiro (horário início/fim, local, atividade). Campos de nível DIA acrescentados em 2026-07 (migration 001): `ano`/`numero` (numeração oficial), `fiscal_pessoal_id`/`adjunto_pessoal_id` (id do cadastro, fonte de verdade para o PDF montar "graduação + nome de guerra"), `fiscal_exibicao`/`adjunto_exibicao` e `delta07_viatura`. **"Delta 07" é o rótulo operacional do Fiscal de Operações** — mesmo campo, não um papel novo; por isso os campos são `fiscal_*`. O que é de nível VIATURA vive no JSONB de cada viatura, não em coluna: `bairro_id`, `comandante_pessoal_id`, `comandante_exibicao`, `avisos_ids[]`, `versao`, `status_envio`, `gerado_em`, `hash_conteudo`. Motivo: um cartão é um DIA com N viaturas, e status/versão do PDF são por viatura — em coluna valeriam para o dia inteiro e quebrariam o `_v2` individual. Viaturas gravadas antes da migration não têm esses campos e **não há migração de boot preenchendo** (reescreveria todos os cartões à toa): todo leitor trata a ausência com `|| ''`. Campos de cabeçalho `fiscal`, `adjunto`, `oficial_sobreaviso` guardam o **nome** da pessoa selecionada (não um id — mantém compatibilidade com cartões antigos que tinham texto livre). Também serve de **padrão**: `is_template` (bool), `nome_template`, `tipo_periodo` (`semana` | `fim_de_semana`), `qtd_viaturas_base` (5/6/7), `origem_template_id` (rastreia de qual padrão um cartão do dia foi clonado). Padrões têm `data: null` e nunca aparecem nas listagens normais por data.
  - **Padrão único (2026-07, migration `002_cartao_padrao_unico.sql`):** coluna `padrao_ativo` (boolean) restrita a `is_template=true` (CHECK `cartoes_padrao_so_template`), com índice único parcial `ux_cartoes_padrao_unico` garantindo **um só** `padrao_ativo=true` no sistema inteiro. A troca é feita **só** pela função `ativar_cartao_padrao(p_id)` (plpgsql, `security definer`, revogada de `anon`/`authenticated`) — nunca por dois `UPDATE` separados: índice único não é deferível, e duas chamadas HTTP sequenciais deixariam uma janela sem padrão nenhum. Templates nomeados múltiplos continuam existindo (histórico de padrões, ver `GET /api/cartoes/templates`), mas só o `padrao_ativo` é usado para clonar o cartão do dia — o antigo fluxo "Copiar de qualquer cartão" (`copiar_de`) e a rota `POST /api/cartoes/:id/clonar` foram **removidos**.
- **`sessoes`** — tokens de autenticação ativos (expiram em 12h).
- **`config`** — `cota_mensal_diarias`.

### Regras de negócio importantes

- **Diária:** `qtd_aparicoes * 2`, sempre. Não mexer nessa fórmula sem confirmar com o usuário. **Diária é das `operacoes`, não dos `eventos`** (eventos civis não geram diária). No Planejador: `total_consumido` = soma real das escalas das operações que já têm escala; `total_planejado` = soma de `qtd_diarias_estimada` só das operações **sem** escala. Nunca a mesma operação nos dois — evita contagem dupla. Ver `diariaDaOperacao` no `server.js`.
- **Não existe mais status de evento nem Kanban de Ordem de Serviço** — foi removido deliberadamente (era `status_os`/`codigo_os`/Kanban no Dashboard). Não reintroduzir sem pedido explícito do usuário. No lugar: `num_os_manual` e `num_sei`, campos de texto livre preenchidos manualmente. O Dashboard alerta quando um evento próximo/em andamento está sem Número da OS e/ou Número SEI informado (calculado, não é status manual).
- **Praça x Oficial no Cartão Programa:** se o Fiscal de Operações selecionado for classificado como `Praça` (posto/graduação até Subtenente) e o campo Oficial de Sobreaviso estiver vazio, o sistema mostra um alerta **não-bloqueante** no painel de Alertas de Conflito do Cartão — não impede salvar.
- **Padrão único de Cartão Programa (2026-07):** um único padrão global ativo por vez (ver `cartoes.padrao_ativo` em "Modelo de dados"). `POST /api/cartoes` (sem `is_template`) **sempre** clona o padrão ativo — 409 tratado (nunca 500) se não houver nenhum. P3 troca o padrão ativo em `PUT /api/cartoes/:id/padrao-ativo` (`exigirP3`), um clique na tela ("Definir como padrão" no painel de Templates). O clone zera `comandante` e o controle de envio (`camposEnvioIniciais()`), herda `bairro_id`/`tipo_periodo`/`qtd_viaturas_base` e grava `origem_template_id`. **Não há mais** busca por tipo de período/quantidade de viaturas nem cópia de "qualquer cartão existente" — a UI (`CriarDoPadrao.tsx`, antigo `SugestaoTemplate.tsx`) só mostra o padrão ativo e um botão "Criar Cartão do Padrão". `tipo_periodo` continua editável no cabeçalho via `PUT /api/cartoes/:id` (Adjunto pode).
- **Perfis de acesso:**
  - `P3` — acesso total (admin), incluindo Cadastro de Pessoal, Cadastro de Bairros e gestão de Templates/Padrão do Cartão Programa.
  - `Adjunto` / `Oficial` — só veem Meu Turno, Cartão Programa, Listar Eventos e Mapa (leitura). Cartão Programa é a única coisa que eles podem *editar* — inclusive criar o cartão do dia a partir do padrão ativo, que não exige P3 de propósito. A aba **Operações** é P3-only. **Exceção deliberada: Cadastro de Viaturas** também fica aberto a Adjunto/Oficial — podem cadastrar e editar viaturas (não só ler); só a exclusão é P3-only (`DELETE /api/viaturas/:id` com `exigirP3`; `POST`/`PUT` de propósito sem o middleware).
  - **Middleware `exigirEdicaoCartao` (2026-07):** as 8 rotas de escrita de viatura/item/cabeçalho do cartão (`PUT /api/cartoes/:id`, `POST`/`PUT`/`DELETE` de `/viaturas` e `/viaturas/:vid/itens`) bloqueiam `Oficial` (403) — antes não checavam perfil nenhum. Cada handler também bloqueia `Adjunto` inline quando `cartao.is_template=true` (só P3 edita um padrão). **Nunca usar `exigirP3` aqui** — bloquearia o Adjunto, que por decisão de produto edita o Cartão Programa do dia livremente.
  - **Janela de exclusão do Cartão Programa (2026-07):** o Adjunto pode excluir o cartão de **um dia** até as **07h00 do dia seguinte** à data do serviço; depois disso o roteiro já foi cumprido e vira registro histórico, e só o P3 exclui. Template segue P3-only em qualquer horário (é estrutura reaproveitada, não roteiro de um dia). Oficial não exclui. `America/Fortaleza` é **UTC-3 fixo** (sem horário de verão desde 2019), então o offset é literal — sem lib de fuso, o que importa porque a Vercel roda em UTC. Regra duplicada nos dois lados: `dentroDaJanelaExclusaoAdjunto` em `server.js` (decide) e `client/src/lib/janelaCartao.ts` (só esconde o botão).
- **Janela de 24h do Cartão Programa (2026-07):** a janela do cartão vai das **07h00 da `data`** até **07h00 do dia seguinte** — não é um dia de calendário. A ordenação do roteiro (`ordenarPorTurno` em `server.js`, aplicada na leitura e ao inserir/editar item) usa a âncora circular `((minutos - 420) + 1440) % 1440`: um item às 06h30 ordena depois de um às 23h00. `client/src/lib/janelaCartao.ts` espelha isso na exibição — `janela24h(data)` formata o período completo ("05/08/2026 07h00 às 06/08/2026 07h00", nunca a data isolada) e `marcarViradaDeDia(itens, data)` intercala um marcador textual (`— 06/08 —`) entre o último item de hoje (≥07h00) e o primeiro de amanhã (&lt;07h00), sem agrupar nem reordenar. Consumido em `CartaoHeader.tsx`, `ViaturaRoteiroCard.tsx`, `pdf/cartaoPdfDados.ts` (campo `janela`) e na Central de Impressão.
- Controle de acesso é **client-side (classe `hidden-role`) E server-side (middleware `exigirP3`)** — sempre implementar os dois lados, nunca confiar só no frontend.

## Segurança (já implementada — não regredir)

- Senhas com hash `scrypt` (nunca texto puro). Migração automática de senhas legadas roda no boot do servidor.
- Sessões via token Bearer, expiram em 12h, invalidadas no logout. Sessões expiradas de qualquer usuário são apagadas globalmente no boot do servidor (dentro do IIFE `inicializar()`), além da limpeza pontual das sessões expiradas do próprio usuário que já acontecia a cada login.
- Toda rota `/api/*` (exceto `/api/login`) exige token válido (middleware `autenticar`), que popula `req.user = { usuario, role, nome }`.
- Rotas de escrita administrativas exigem `exigirP3`. `POST /api/cartoes` faz a checagem de role manualmente dentro do handler (em vez de usar o middleware) só quando `is_template` é true, porque a mesma rota também cria o cartão do dia — que Adjunto/Oficial podem criar livremente — ler o handler antes de assumir que uma rota tem ou não restrição. `DELETE /api/cartoes/:id` usa o middleware `exigirP3` para qualquer cartão (template ou do dia) — apagar o roteiro operacional de um dia é destrutivo e não faz parte da edição diária que Adjunto/Oficial têm permissão de fazer no Cartão Programa.
- **Toda inserção de dado do usuário no DOM passa pela função `esc()`** (escape de HTML) em `app.js` — proteção contra XSS. Ao adicionar `innerHTML` novo, sempre envolver valores dinâmicos com `esc(...)`.
- Senha mínima: **3 caracteres** (decisão deliberada, para não quebrar a senha padrão `123` já usada pelo batalhão — não "corrigir" para 4+ sem perguntar).
- **RLS habilitado em todas as tabelas públicas** (migration `ativar_rls_tabelas_publicas`, 2026-07), **sem policies**. O `service_role` que o `server.js` usa tem `BYPASSRLS`, então RLS não afeta nenhuma rota do backend; sem policy, os roles `anon`/`authenticated` ficam totalmente bloqueados no acesso direto ao Supabase (o frontend não fala com o Supabase direto). Isso fecha o alerta `rls_disabled_in_public` do Supabase. Ao criar tabela nova, habilitar RLS nela também (`ALTER TABLE ... ENABLE ROW LEVEL SECURITY`, sem policy) — ver bloco no fim de `supabase/schema.sql`. **Não** criar policies sem necessidade real (quebraria o padrão de autorização feito no Express).

## Convenções de código

- **Idioma:** português em tudo — variáveis, funções, comentários, textos de UI. Não anglicizar.
- **Chamadas à API no frontend:** sempre via `apiFetch()` (wrapper que injeta o token e trata sessão expirada), nunca `fetch()` puro.
- **Shell do redesign (sidebar/topbar, 2026-07):** a sidebar tem, de cima pra baixo, `.brand` (brasão real em `public/img/brasao-5bpm.png` sobre fundo gradiente — o original do handoff tinha 1920×2192/3,9 MB e foi reduzido para 112×128/20 KB; **não** trocar pelo arquivo cru de `uploads/`), `.perfil-card` (identidade do usuário), o menu, `.cota-card` (anel de cota mensal, **P3-only** via `hidden-role` alternado em `applyRolePermissions`, alimentado por `atualizarCotaSidebar()` a partir do `dashboard-resumo`) e o `.sidebar-footer`, que agora só tem ações (Alterar Senha / Sair). A topbar tem `.tema-toggle` (toggle segmentado Claro/Escuro com `role="radiogroup"`, substituiu o antigo `<select>` de tema), `.topbar-data` e `.profile` com nome + cargo. No mobile (`max-width:768px`) `.topbar-data`, `.profile-texto` e os rótulos do toggle somem — não cabem junto do título.
- **Design system / cores (redesign 2026-07):** a paleta vem do handoff `Redesign projeto sgo-5bpm/design_handoff_sgo_5bpm/README.md` — **light-first**, primária azul `#2563EB`, superfícies brancas, tipografia **Inter** (família única; a Outfit saiu, `--font-title` virou alias de `--font-body` e continua existindo só pra não quebrar as regras que a usam). São **dois temas**: sem classe no `<body>` = Claro (padrão), `.tema-escuro` = escuro azulado. A classe legada `.tema-claro` não existe mais; `carregarPrefsTema()` em `app.js` mapeia o valor legado `'padrao'` do localStorage para `'claro'`. Dark **não é inversão**: superfícies viram cinza-azulado (`#0B1220`/`#151E30`), o acento clareia e os status viram tintas translúcidas ~16%.
  - **Nunca escrever cor crua numa regra de componente** — sempre `var()`. Um literal que assume fundo escuro (`rgba(255,255,255,.05)`, `#fca5a5`) quebra no tema claro, que agora é o padrão. Exceções legítimas: o bloco `.rel-pdf-*`/`@media print` (preto no branco é proposital) e as cores de marcador do Leaflet em `app.js`.
  - **Pares `--x` / `--x-fg`:** a var sólida (`--success`, `--danger`, `--info`, `--primary-solid`) é **fundo com texto branco em cima** (badge/botão); a `-fg` (`--success-fg`, `--danger-fg`, `--warning-fg`, `--info-fg`) é **cor de texto/ícone sobre o tint `-bg`**. Trocar uma pela outra é o erro mais comum aqui e sempre reprova contraste em um dos temas.
  - `--primary` é o acento (ícone, borda, texto) e **clareia para `#3B82F6` no tema escuro**; `--primary-solid` é o fundo de botão/avatar e fica `#2563EB` nos **dois** temas de propósito — `#3B82F6` com texto branco dá só 3.68:1 e reprova AA.
  - **Contraste é requisito, não preferência:** vários tokens ficaram deliberadamente um tom mais escuros que o handoff porque o valor original reprova WCAG AA (`--text-muted` `#5B6478` em vez de `#64748B`; `--success` `#15803D` em vez de `#16A34A`; `--info` `#0369A1` em vez de `#0EA5E9`). Cada um tem o motivo em comentário no `:root`. Ao mudar cor, revalidar — a auditoria completa (11 abas × 2 temas) fecha hoje com **zero** reprovações AA.
- **Handlers de clique: nada de `onclick=""` inline.** A CSP (`server.js`) tem `script-src` sem `'unsafe-inline'`, então handler inline **não dispara**. Todo botão renderizado dinamicamente usa `data-action="..."` (+ `data-*` para os argumentos, lidos via `el.dataset`) e é despachado por um **único listener delegado em `document`** (no bloco `DOMContentLoaded` de `app.js`, `switch (d.action)`). `document` é o pai estável — sobrevive ao `innerHTML` reescrito das listas. Ao criar um botão novo: adicionar o `case` no switch e passar os dados por `data-*` com `esc(...)` (nunca concatenar argumento em string inline — quebra com aspas/apóstrofo).
- **Modais:** padrão `.modal-overlay` + `.modal-box`, toggle via classe `hidden`. Ver `modal-usuario`, `modal-pessoa`, `modal-novo-template`, `modal-relatorio-sei` como referência.
- **Drawers/off-canvas:** três componentes distintos, não confundir — `#drawer` (gaveta de detalhes de **evento**, `openDrawer(eventId)`/`closeDrawer()`, só alocação agregada, sem escala); `#drawer-op` (gaveta de detalhes de **operação**, `openDrawerOperacao(id)`/`closeDrawerOperacao()`, com bloco "Efetivo Escalado" que reaproveita os mesmos ids do form de escala — `form-escala`/`escalas-list`/`esc_*` — que só existem nessa gaveta agora); `.sidebar`/`#nav-drawer-overlay` (classes `.nav-drawer-open`/`.open`, `abrirNavDrawer()`/`fecharNavDrawer()`) é o menu de navegação mobile, só ativo em `@media (max-width:768px)` — em desktop a sidebar continua fixa, sem drawer. Ambos usam a mesma técnica visual (wrapper fixo + overlay com fade + painel deslizando via `transition`), mas com nomes de classe/função próprios de cada um.
- **Painéis colapsáveis** (Histórico do Cartão, Templates, Gerenciar Bairros): botão toggle + `panel.classList.toggle('hidden')`, renderiza sob demanda só quando abre.
- **Autocomplete customizado** (form "Escalar Militar" na `#drawer-op`): o campo Nome (`#esc_militar_nome`, `.autocomplete-wrap`) filtra `state.pessoal` por nome/`nome_guerra`/`matricula` (via `normalizarTexto`, acento- e case-insensitive) e mostra um dropdown próprio (`#escala-autocomplete-results`, `.autocomplete-item`) — substitui o `<datalist>` nativo (ruim no mobile). Funções `renderAutocompleteEscala`/`selecionarMilitarEscala`/`limparAutocompleteEscala` em `app.js`; seleção via `data-action="selecionar-militar-escala"` no listener delegado; navegação por teclado (setas+Enter) e fecha ao clicar fora/Esc. Selecionar trava a matrícula (`readOnly`) só se o militar tiver matrícula; limpar o nome libera de novo (permite escalar militar fora do cadastro por digitação livre). Chamar `limparAutocompleteEscala()` em todo reset do `form-escala`. Padrão reaproveitável para outros autocompletes (classes `.autocomplete-*` genéricas em `style.css`).
- **Toasts:** `showToast(mensagem, tipo)` — tipos: `success`, `info`, `warning`, `danger`.
- **Badges de tipo/status:** classe CSS gerada via slug (minúsculo, espaço→hífen, remove acento com `normalize("NFD")`). Ao adicionar um novo tipo/atividade/categoria, lembrar de adicionar a cor correspondente em `style.css`. Exceção: as 5 categorias operacionais do Cadastro de Pessoal (`.badge.pcat-*`, variáveis `--badge-categoria-1..5`) usam um mapa fixo (`CATEGORIA_PESSOAL_BADGE_MAP` em `app.js`) em vez do slug automático, porque os nomes têm preposições/acentos que não convertem de forma previsível.
- **Gráficos:** sem lib externa — SVG gerado à mão em JS (ver `renderSazonalidadeChart` em `app.js`), consistente com o resto do projeto (mini-barras em CSS já usadas em Estatísticas/Planejador).
- **Mapa:** Leaflet via CDN, dois estilos de tile (`dark_all` e `voyager` do CartoCDN), overrides de tema em `style.css` (`.leaflet-popup-*`, `.mapa-*`). Sem preferência salva, `carregarPrefsMapa()` sugere o tile pelo tema global — como o padrão agora é claro, o padrão de mapa passou a ser o `voyager` (colorido); depois que o usuário mexe no seletor, a escolha salva prevalece.
- **Toda funcionalidade nova** deve funcionar corretamente nos dois lados de sessão: o que o `P3` vê/edita e o que `Adjunto`/`Oficial` vê (geralmente menos).
- **Migrações de schema:** IIFE no topo do `server.js` (junto das outras, ex. `normalizarCamposTemplateCartao`, `seedBairrosCoordenadas`) que roda no boot, lê o db, adiciona campos faltantes com `if (!('campo' in obj))`, e só grava (`writeDB`) se algo mudou. Nunca destrutivo.

13. **Alertas** (`client/src/pages/modulos/avisos/`, renomeado de "Avisos Operacionais" em 2026-07 — **só o texto visível mudou**: tabela `avisos`, colunas, rotas `/api/avisos`, `avisos_ids`, `SectionId: 'avisos'` (é a URL) e todo identificador técnico continuam com o nome antigo) — orientações da P3 por bairro e/ou Companhia, que entram no Cartão Programa das viaturas alocadas naquela área. **Leitura para todos os perfis** (o Adjunto precisa consultar para selecionar no cartão; o Oficial, para saber o que foi orientado ao turno), **escrita só P3**. A aba tem filtros por bairro/Companhia/prioridade, alternador "Só vigentes" e o painel **"Vencendo nos próximos 7 dias"** (P3-only) com renovar por 30 dias ou encerrar. Fica só no menu lateral — a barra inferior do celular já tem seus 4 destinos + Mais.
    - **Desambiguação de nome (2026-07):** "Alertas" já era usado para o que o *sistema* detecta, não o que a P3 escreve — por isso, ao mesmo tempo, o painel "Alertas de Conflito" do Cartão virou **"Conflitos"** (`TrilhoCartao.tsx`/`ConflitoBanner.tsx`) e o card "Alertas Operacionais" do Dashboard virou **"Pendências"** (`AlertasEPatrulhamento.tsx`); o mesmo painel em Meu Turno (conflitos do cartão + eventos sem OS/SEI, não avisos da P3) virou **"Pendências do Turno"**.
    - **Quais avisos chegam a uma viatura** (`bairrosDaViatura`/`avisosDaViatura` em `client/src/lib/avisos.ts`), em ordem de confiança: (1) o `bairro_id` explícito; (2) o `setor` casado por nome normalizado — rede de segurança, porque nenhuma viatura anterior à migration tem `bairro_id` e sem isso o módulo nasceria inerte; (3) os bairros citados nos locais do roteiro, que também cobre "a viatura atua em mais de um bairro". Quando a área vem só por nome, o painel avisa na tela. Mais os avisos de Companhia sem bairro.
    - **Regras fixas:** teto de **4 alertas por cartão** (protege a página única — aplicado no cliente E no servidor), texto ≤240 caracteres, prioridades `alta`/`critica` pré-marcadas e `informativa`/`atencao` visíveis mas desmarcadas. A viatura guarda só `avisos_ids`; o **texto nunca é duplicado** no JSONB, então o cartão sempre reflete o texto atual e alertas encerrados somem da geração.

Concentra as saídas oficiais do Cartão Programa: seleção de data, tipo de saída, filtro Conteúdo/Recorte (reusa `pdf/geracaoCartao.ts`) e seleção múltipla de viaturas. Design institucional próprio (`.impressao-*` em `style.css`) — brasão, órgão/unidade, tipo de documento, janela de 24h completa, número quando houver, emissão congelada no mount — distinto tanto de `.rel-pdf-*` (relatórios SGEPM) quanto de `.cp-*` (Cartão em PDF por viatura). Só **duas saídas** existem: "Cartão Individual" (`SaidaCartaoIndividual.tsx`, envolve `pdf/DocumentoCartoes.tsx` já existente, não modificado) e "Consolidado do Dia" (`SaidaConsolidadoDia.tsx`: Quadro Resumo + roteiro por viatura + assinatura do Chefe da 3ª Seção — **sem** rota nova no backend). As saídas de escala de serviço, mapa de diárias e mapa de força/efetivo **não existem**: o SGO não tem guarnição completa por viatura nem efetivo previsto/disponível/indisponível — não implementar sem antes decidir a fonte desses dados com o usuário. Gate de impressão em `print.css` usa a técnica `visibility:hidden` em tudo + `visibility:visible` só em `#impressao-preview-area` (diferente do padrão `body:has(#modal-id)` dos outros dois, porque `/impressao` vive dentro do `AppLayout` normal, não é modal).

## Relatórios PDF (estilo SGEPM)

> **Exceção deliberada (2026-07): o Cartão Programa em PDF NÃO segue este padrão.** Ele não é impresso — é gerado e mandado pelo WhatsApp ao comandante de cada viatura, que o lê na tela do celular em serviço. Por isso tem design próprio (página de **100×180 mm**, coluna única, sem caixas, Inter em dois pesos, uma única cor institucional) em `client/src/pages/modulos/cartao/pdf/` + bloco `.cp-*` no `style.css`. Mudança no cartão **não** propaga para os três relatórios abaixo, nem o contrário. Foi pedido explícito do usuário; não "uniformizar" sem novo pedido.

> **Terceiro padrão de impressão (2026-07): a Central de Impressão (`/impressao`, ver "Módulos principais" item 14) também não segue nenhum dos dois.** Tem seu próprio design institucional (`.impressao-*`) para as saídas 1 e 2 do Cartão Programa, embora a saída 1 reaproveite o `.cp-*` por dentro (ver item 14). Três designs de impressão coexistem de propósito — não uniformizar sem pedido explícito.

> **`print.css` (2026-07):** as regras `@page`/`@media print` de todos os três padrões (SGEPM, Cartão, Central de Impressão) foram extraídas de `style.css` para `client/src/print.css`, importado depois de `style.css` em `main.tsx` — a ordem de import define a cascata. As regras **base** (`.rel-pdf-*`, `.cp-*`, `.impressao-*`, `.folha`), usadas também na prévia em tela, continuam em `style.css`. Ao adicionar novo CSS de impressão: `@page`/`@media print` vai em `print.css`; o resto (cor, layout, tipografia visível em tela) vai em `style.css`. **Cuidado com `*/` dentro de comentários CSS** — fecha o comentário antes da hora e quebra o build do `lightningcss` sem aviso óbvio (já aconteceu).

Os antigos botões de texto "SEI" (Gerar Relatório para SEI / Lista para SEI em Listar Eventos, Relatório SEI nas gavetas de evento/operação, Copiar Texto Formatado no Relatório Diário) foram **substituídos por relatórios em PDF** inspirados no relatório oficial SGEPM (cabeçalho azul-marinho `#002145`, tabela zebrada `#F5F7FA`, A4 paisagem, Helvetica), gerados via `window.print()` (Salvar como PDF). **Todos os relatórios PDF compartilham o mesmo design** (é requisito do usuário — nenhum relatório pode ficar fora do padrão). Três relatórios:
- **"Relatório de Eventos (PDF)"** (Listar Eventos) — `gerarRelatorioPdfEventos()`, colunas Nº · Data · Nº OS · Nome do Evento · Endereço/Local · Nº SEI, respeitando o filtro ativo (`getEventosFiltrados()`).

Os três injetam HTML em `#relatorio-pdf-area` (dentro do modal único `#modal-relatorio-pdf`) via `abrirRelatorioPdf()` + `cabecalhoRelatorioPdf(titulo, sub)` (+ `.rel-pdf-tabela` e, quando há total simples, `.rel-pdf-rodape`). **Mudança de design de relatório vale para todos:** alterar `cabecalhoRelatorioPdf` e/ou as classes `.rel-pdf-*` (compartilhadas) já propaga para os três — só tratar um relatório isoladamente se o usuário pedir explicitamente. Ao criar um relatório PDF novo, reusar esses helpers/classes, nunca montar HTML/CSS do zero. Impressão isolada com o mesmo padrão do antigo modal SEI: `@media print { body:has(#modal-relatorio-pdf:not(.hidden)) ... }` esconde `.app-container` e mostra só a área, com `@page relatorioPdfLandscape { size: A4 landscape }` e `print-color-adjust: exact` (para o cabeçalho marinho/zebra saírem coloridos).

## Fluxo de trabalho recomendado ao editar

1. Ler o trecho relevante antes de editar (arquivos grandes — usar Grep para localizar, não abrir tudo).
2. Depois de editar `.js`, rodar `node --check <arquivo>` antes de testar no navegador.
3. Reiniciar o preview server (`server.js` não tem hot reload).
4. Testar de ponta a ponta no navegador (login, ação, verificação visual) — não declarar "pronto" sem isso. Testar com clique real (preview_click/preview_fill), não só chamando a função handler direto por `preview_eval` — já aconteceu de um fluxo funcionar via chamada direta e mascarar um problema de timing no clique real.
5. **Sempre limpar dados de teste** criados durante a verificação (eventos, cartões, templates, pessoal, bairros fictícios) antes de encerrar — o preview local aponta pro mesmo Supabase de produção (mesmas credenciais em `.env.local`/`.claude/launch.json`), não é um ambiente descartável. Exceção: quando o próprio usuário pede explicitamente para popular dados fictícios/demo — aí é pra manter.
6. Testar nos dois perfis relevantes quando a mudança afeta permissões (P3 e Adjunto).
7. Antes de mexer ou apagar qualquer registro no Supabase, checar se os dados batem com o que você mesmo criou nesta sessão — pode haver uso real do app em paralelo (outro servidor do usuário rodando, ou a própria produção na Vercel). Se encontrar registro que você não reconhece ter criado, não delete: avise o usuário.
8. Depois de validar localmente, `git add`/`commit`/`push` para `main` — a Vercel publica automaticamente via integração Git (ver seção "Stack e arquitetura"). Não fazer push sem o usuário saber que aquilo vai pra produção.

## Pendências em aberto 

Nenhuma pendência de arquitetura estrutural em aberto no momento. Cadastro de Viaturas/Frota já existe (ver seção "Módulos principais"), e o Cadastro de Pessoal já foi populado com o efetivo geral do batalhão (244 militares importados do relatório SGEPM em 2026-07, com campo `matricula`) — a maioria sem `categorias` (efetivo geral sem papel operacional ainda; ver nota em "Modelo de dados").

**Paginação de Listar Eventos (aberto):** o protótipo do redesign tem paginação e o app não. Com 464 eventos cadastrados, a aba renderiza **todas as linhas de uma vez** — no celular (layout `table-cards-mobile`) isso dá ~120.000px de rolagem. Não foi implementado junto do redesign por ser mudança funcional, mas é o item de UX mais concreto que sobrou. Ao implementar, a paginação precisa conviver com `getEventosFiltrados()`, que também alimenta o Relatório de Eventos (PDF) — o PDF deve continuar exportando o **filtro inteiro**, não só a página visível.

**Redesign — shell mobile (2026-07):** além do desktop, o app tem o shell mobile do handoff (`* Mobile.dc.html`), ativo em `@media (max-width:768px)`: a topbar branca vira **faixa azul** (`--primary-solid`) com o título da tela, e existe uma **barra de abas inferior** (`.bottom-tabs`, fixa) com 5 destinos. Os destinos são **montados por perfil** em `montarBottomTabs(role)`: P3 = Início(Dashboard)/Eventos/Operações/Cartão/Mais; Adjunto e Oficial = Meu Turno/Cartão/Eventos/Mapa/Mais — sem Dashboard nem Operações, que são P3-only. "Mais" abre o mesmo drawer da sidebar, que continua sendo o acesso ao resto das abas. `sincronizarBottomTabs()` mantém a aba inferior marcada em sintonia com o `.nav-btn.active` (chamado no handler de troca de aba). O `.tab-content` ganha `padding-bottom` no celular pra o conteúdo não ficar sob a barra fixa. **Ao criar uma aba nova, decidir se ela entra na barra inferior ou fica só no drawer** — a barra comporta 4 destinos + Mais.

**Cuidado de contraste no header azul:** a faixa é azul nos **dois** temas, então elementos sobre ela não podem usar tokens que acompanham o tema. O avatar usa `--primary-fg` de fundo com `--primary-solid` de texto — o quadrado translúcido do protótipo dava 3.76:1, e `--bg-panel` invertia no tema escuro (3.22:1).

**Itens de auditoria de segurança/performance adiados (2026-07):** uma auditoria aplicou correções em 4 lotes (backup sem senha/sessão + leituras pontuais; trust proxy + senha mínima de 8; sanitização de badge + `tipo_evento` fechado + indexação das agregações; SRI nos CDNs + polling pausado com aba oculta). Ficaram **deliberadamente fora de escopo** desta rodada, para fases próprias:
- **S1 — CORS sem `Origin`:** `origemPermitida` devolve `true` quando não há header `Origin` (curl/apps nativos). Comportamento mantido de propósito; a autorização real é por token, não por CORS.
- **S2 — token em `localStorage`:** migrar o token de sessão de `localStorage` para cookie `HttpOnly` é mudança estrutural de auth (fase própria).
- **S4 — `'unsafe-inline'` no `style-src`:** só sai depois de migrar dezenas de `style=` inline para classes (junto da fase de design/Plano 3).
- **P2 — aposentar `writeDB` de vez:** as rotas de escrita de tabela única já usam `writeRow`/`readTabela`, mas as agregadoras e as demais ainda usam o shim `readDB()`/`writeDB()`. Substituição total fica para a fase de performance.
- **P5 — índices/paginação no Supabase:** sem índices dedicados nem paginação nas listagens grandes; fase de performance.
- **S10 — confirmar RLS em produção:** verificar via `get_advisors` (Supabase MCP) que o `rls_disabled_in_public` está fechado — exige aprovação manual do tool call, apenas reportar, sem alterar nada.

**Separação Eventos/Operações (concluída em 2026-07):** a diária saiu dos eventos e passou para a nova entidade `operacoes` (registro único planejamento→execução). A antiga `missoes_planejadas` foi migrada para `operacoes` e a tabela ficou **órfã no banco** (dados migrados, sem `DROP` — rede de segurança, mesmo padrão da antiga tabela de auditoria; não recriar dependência nela). O `data/db.json` legado segue preservado. Se algum dia for dar `DROP TABLE missoes_planejadas`, confirmar antes com o usuário.

Ideias sugeridas e ainda não priorizadas pelo usuário: Setores de Patrulhamento com vínculo N:N a Bairros, Demandantes, Modalidades de Policiamento, para eliminar texto livre restante em outras telas (demandante do evento, modalidade de policiamento).
